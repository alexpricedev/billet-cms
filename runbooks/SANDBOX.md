# The sandbox: fixtures, Northwind Studio and persona sessions

A fixture site and the CMS, running together on one local database and holding
the same people and content every time. It exists so that anyone (an agent, a
reviewer) can sign in as a persona and run the stories in `ux/stories/`.
`ux/personas.md` is the source of truth for who and what is in it.

**Dev and test only.** The loader truncates the CMS's content tables *and the
fixture site's `users` table*. It must never touch a real site's database.

## Commands

```bash
bun run sandbox     # load fixtures, start the site and the CMS, print both URLs
                    # and the personas' sign-in emails
bun run fixtures    # reload the data only
bun run scripts/persona-session.ts leo --side site   # prints  site_session=<id>
bun run scripts/persona-session.ts leo --side cms    # prints  northwind_cms_session=<raw>
```

Needs a Postgres that `DATABASE_URL` (from `.env`) points at, e.g. `createdb
cms_dev`. `bun run sandbox` builds the CMS assets on first run, so pages are
styled; Ctrl-C stops both servers.

| | Default | Override |
|---|---|---|
| Site (Northwind Studio) | `http://localhost:3001` | `SANDBOX_SITE_PORT` |
| CMS | `http://localhost:3000` | `SANDBOX_CMS_PORT` |
| Uploaded media | `.sandbox/media` (git-ignored) | `SANDBOX_MEDIA_DIR` |

Use the default ports when you can: a printed cookie is for `localhost`, and
the stored image URLs name the site's port.

A reload (`bun run fixtures`) while the sandbox is running resets the data, but
the site keeps its cache until it sees `content_version` change, and the loader
pins that value. Restart `bun run sandbox` instead (it reloads on start).

## Signing in as a persona

The cookie is printed on stdout as `name=value` (hints go to stderr), so
`$(...)` captures only the cookie. Set it in the browser for `localhost`, or
send it as a `Cookie` header.

- `--side site`: the site's own session. Start story 01 here: open the site's
  home page and press **Edit content**. Or skip the cookie and sign in at
  `http://localhost:3001/login` with the persona's email.
- `--side cms`: a CMS session, skipping the handoff. Every editor has one with a
  fixed value straight after a load. **Tom has none**: he is a site user who is
  not in `cms_identities`, so the script refuses.

## What the fixtures hold

Everything has a fixed id and timestamp; loading twice gives identical rows
(`fixtures/fixtures.test.ts` checks it).

- **Definitions** (from `e2e/cms.config.ts`, published by the loader): blocks
  `hero`, `text`, `gallery`, `quote`, `cta`; slots `home.hero` and `footer.cta`;
  page types `landing` and `article`.
- **`home.hero`**: published "We make websites that last", with a newer draft
  "Websites that outlast the trend". `footer.cta` is published.
- **Pages**: `/about` (published), `/work` (three revisions, the middle one
  published, the newest a draft), `/draft-ideas` (never published), `/long-title`
  (published; a 200-character title with emoji).
- **Redirect**: `/our-work` → `/work`. (Not `/studio`: story 08 moves `/about` there.)
- **Images** (all JPEG, generated by `fixtures/images.ts`): `harbour` (home hero),
  `team` (used on `/about` and `/work`), `project` (`/work`), `portrait` (300 px
  wide, too narrow for the hero's 400 px, used nowhere), `office` (used
  nowhere), `sketch` (only the `/draft-ideas` draft uses it).
- **Export tokens**: "Preview environment" (live; raw value
  `nw-live-export-token-0123456789abcdef`) and "Old laptop" (revoked).

## Uploads without a bucket

The CMS stores media in S3. For the sandbox, `MEDIA_LOCAL_DIR` writes the same
objects to a directory instead, and `MEDIA_PUBLIC_BASE_URL` names where they are
served: the fixture site serves the directory at `/media/*`. It is for
development and tests only: with `NODE_ENV=production` the CMS ignores
`MEDIA_LOCAL_DIR` (with a warning), so the no-bucket refusal stays. The site's
CSP `img-src` picks the site's origin up from `MEDIA_PUBLIC_BASE_URL`.

## The guards

`bun run sandbox`, `bun run fixtures` and `persona-session` all refuse, with a
message and a non-zero exit, when:

- `NODE_ENV=production`; or
- the `DATABASE_URL` host is not `localhost`, `127.0.0.1` or `::1`. The message
  names the host. `FIXTURES_ALLOW_REMOTE=1` overrides this check (and only this
  one).

The check (`scripts/sandbox-guard.ts`) runs before anything that opens a database
pool is imported: `app`'s database module connects as soon as it loads, so each
script loads the rest with a dynamic `import()` after the guard.

## Resetting

`bun run fixtures` truncates and reloads everything, uploads included
(`.sandbox/media/media` is emptied). To start from nothing, drop and recreate the
database.

## How it fits together

- `e2e/` is the fixture site: `e2e/cms.config.ts` its definitions, `e2e/site.ts`
  its server. The e2e suite and the sandbox share it.
- `fixtures/` is the data as code (`personas.ts`, `images.ts`, `content.ts`) and
  the loader (`load.ts`). It writes by SQL, because the CMS's services mint ids
  and use `now()`. It also writes the site's `users`, which is why the guards
  exist.
- `scripts/` holds the entry points and the guard.
- The CMS and `persona-session` share a pinned `CRYPTO_PEPPER`
  (`fixtures/constants.ts`); the CMS's cookie is `northwind_cms_session` and the
  site's is `site_session`, so the two don't collide on `localhost`.
